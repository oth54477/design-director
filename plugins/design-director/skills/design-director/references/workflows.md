# Workflows

## 단계

1. Inspect — context-analysis 와 inspect-skills.py
2. Classify — task, 디자인 시스템 유무, 모션 종류, 지명한 스킬
3. Route — skill-router. 스타일 리드가 둘이면 여기서 멈추고 질문한다.
4. Plan — 유지할 것, 바꿀 파일, 바꾸지 않을 파일, focus
5. Brief — 아래 「실행 전 보고」를 사용자에게 보여 준다. `plan_approval` 이면 승인을 받기 전에는 다음 단계로 가지 않는다.
6. Mockup — `mockup` 이 none 이 아니면 아래 「시안」을 만들어 보여 주고 승인을 받는다.
7. Execute — 고른 스킬만. 감사 라우트와 needs_decision 에서는 하지 않는다. 승인된 계획과 시안의 범위를 넘지 않는다.
8. Render — 브라우저를 실제로 열 수 있을 때만. 도구는 `aside-browser` 가 먼저다(순서는 quality-gates 마지막 절). 아니면 static 이라고 적는다.
9. Audit — guidelines, 그리고 라우트에 impeccable audit 이나 review-animations 가 있을 때
10. Repair — P0, P1 만, 최대 두 번. 감사 라우트에서는 건너뛴다.
11. Verify — 고친 항목만 다시 본다. 승인된 시안과 결과 화면이 다르면 그 차이를 적는다.
12. Report — 아래 형식

문서 작업의 검증은 artifact 다. HTML 미리보기를 브라우저로 열었으면 그 사실을 적고, 열지 못했으면 artifact 검사만 했다고 적는다.

## 실행 전 보고 (Brief)

Route 와 Plan 이 끝나면, 하위 스킬의 SKILL.md 를 따라 무엇이든 실행하기 전에 아래를 보여 준다. 감사 라우트도 보여 주되 승인을 기다리지 않고 진행한다(파일을 고치지 않으므로). needs_decision 이면 Brief 대신 선택 질문만 한다.

1. 판정 — task, 디자인 시스템 유무와 그 근거 파일, 모션 종류, 지명한 스킬. 추측한 항목은 추측이라고 쓴다.
2. 고른 스킬 — 각 스킬과 focus, 고른 이유 한 줄.
3. 고르지 않은 스킬 — 특히 스타일 리드를 뺀 이유. missing 이 있으면 이름과 업스트림.
4. 계획 — 바꿀 파일, 바꾸지 않을 파일, 유지할 동작·카피·토큰 이름.
5. 실행할 명령 — 카탈로그에 있는 CLI 중 실제로 돌릴 것. 네트워크 접근(guidelines fetch)과 파일을 만드는 명령은 따로 표시한다.
6. 검증 방법 — browser 또는 static, 쓸 도구.
7. 시안 — image, directions, html-only, none 중 무엇이고 왜인지.
8. 위험·가정 — 범위 밖 파일, 토큰 변경 가능성, 확인하지 못한 것.

승인은 질문 도구가 있으면 그것으로(선택지: 이대로 진행 / 계획 수정 / 중단), 없으면 텍스트로 묻고 멈춘다. 답이 없거나 빈 답이면 진행하지 않는다. 사용자가 요청에서 이미 "바로 진행", "확인 없이" 라고 했으면 Brief 는 보여 주되 기다리지 않고, 그렇게 했다고 보고에 적는다. 계획을 수정하라는 답이면 Classify 또는 Route 부터 다시 하고 Brief 를 다시 보여 준다.

## 시안 (Mockup)

목적은 코드를 쓰기 전에 방향을 눈으로 합의하는 것이다. 시안은 근사치이며 실제 컴포넌트가 아니라고 함께 적는다.

- `directions` — huashu 가 리드면 그 스킬의 세 방향 제시가 곧 시안이다. 따로 만들지 않는다.
- `image` — 아래 절차로 이미지를 만든다.
- `html-only` — 브라우저가 없을 때. HTML 파일 경로만 주고 "렌더해 보지 않음" 이라고 적는다.
- `none` — 모션(정지 이미지로 움직임을 보여 줄 수 없다. Brief 에 타이밍·이징·대상 요소를 글로 적는다), 문서(kami·huashu 산출물 자체가 미리보기다), 감사, needs_decision, 사용자가 시안을 빼라고 한 경우.

`image` 절차:

1. 시안 파일은 저장소 밖에 둔다. 세션 scratchpad 가 있으면 거기, 없으면 임시 디렉터리. 저장소에 커밋하거나 복사하지 않는다.
2. 단독 HTML 한 장으로 만든다. 색·글꼴·간격·radius 는 저장소의 실제 토큰 값을 읽어 쓴다. 디자인 시스템이 있으면 그 토큰 이름과 값만 쓰고 새 값을 만들지 않는다. 쓸 수 없었던 토큰은 시안 보고에 적는다.
3. 기존 화면 개선(improve)이면 지금 화면을 먼저 캡처하고, 같은 폭으로 시안을 캡처해 전/후를 나란히 보여 준다. 지금 화면을 못 열면 시안만 보여 주고 그 사실을 적는다.
4. 캡처는 `aside-browser` 가 먼저다(quality-gates 마지막 절). 폭은 데스크톱 1440, 반응형이 범위에 있으면 390 도 같이. 라이트·다크가 있으면 계획에서 바뀌는 쪽을 둘 다.
5. 이미지 파일을 사용자에게 보낸다(파일 전송 도구가 있으면 그것으로, 없으면 경로). 바뀌는 지점을 번호로 짚은 짧은 설명을 붙인다.
6. 외부 이미지 생성 모델·유료 API 로 시안을 만들지 않는다(security). HTML 렌더만 쓴다.
7. 승인 질문(선택지: 이 시안으로 구현 / 시안 수정 / 중단). 수정이면 시안만 고쳐 다시 보여 준다. 빈 답이면 진행하지 않는다.

구현은 시안 HTML 을 붙여 넣는 것이 아니라 저장소의 컴포넌트와 토큰으로 다시 쓴다. Verify 에서 결과 화면을 같은 폭으로 캡처해 시안과 나란히 비교한다.

## 긴 보고

### Design Analysis

프로젝트 상태, task, 디자인 시스템, 문제. 렌더를 봤는지.

### Skill Selection

고른 스킬과 이유, 고르지 않은 스킬과 이유, 바꿀 범위, missing.

### Design Direction

스타일 리드, 레이아웃, 색과 글자, 컴포넌트와 인터랙션. 기존 토큰을 유지하면 그 이름을 적는다.

### Execution Results

실제로 실행한 명령, 읽기만 한 스킬, 바꾼 파일, 본 화면. 실행하지 않은 CLI 는 실행하지 않음이라고 적는다.

### Quality Report

일곱 항목의 점수 또는 미확인, P0~P3, 고친 것, 남은 위험, 다음 제안. WCAG 준수는 확인한 항목만.

## 짧은 보고

한 구성요소의 작은 수정:

- 고른 스킬
- 바꾼 파일
- 확인한 것
- 확인하지 못한 것

방향 선택이 필요하면 짧은 보고로 줄이지 않고, 선택지와 기본안(기존 시스템 유지)을 먼저 말한다.
